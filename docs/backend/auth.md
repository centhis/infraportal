# Аутентификация и Авторизация

Этот документ подробно описывает механизм аутентификации и авторизации, используемый в бэкенде.

## Обзор

Система безопасности построена на основе **JSON Web Tokens (JWT)** и ролевой модели доступа (RBAC), реализованной через разрешения (permissions).

-   **Аутентификация** — это процесс проверки личности пользователя. Он реализован с помощью пары токенов: `access_token` и `refresh_token`.
-   **Авторизация** — это процесс проверки прав доступа пользователя к определенным ресурсам. Она реализована с помощью списка разрешений, встроенного в `access_token`.

## 1. Процесс аутентификации (Login)

Когда пользователь входит в систему (`POST /api/v1/auth/login`), происходит следующий процесс:

1.  **Верификация**: `AuthService` проверяет предоставленные `login` и `password` пользователя. Пароль сверяется с хешем в базе данных с использованием `argon2`.
2.  **Сбор разрешений**: `PermissionService` выполняет запрос к базе данных, чтобы собрать все разрешения, назначенные пользователю через его группы и роли.
3.  **Создание Access Token**:
    -   Генерируется `access_token` (срок жизни — 15 минут).
    -   В его полезную нагрузку (payload) встраиваются `id` пользователя, `login` и **список его разрешений**.
4.  **Создание Refresh Token**:
    -   Генерируется `refresh_token` (срок жизни — 30 дней).
    -   В базе данных создается запись в таблице `user_sessions`, связывающая `refresh_token` с пользователем, его IP-адресом и User-Agent. Это и есть **сессия**.
5.  **Ответ**:
    -   `access_token` и список разрешений возвращаются в теле ответа.
    -   `refresh_token` устанавливается в `httpOnly` cookie, что делает его недоступным для JavaScript на стороне клиента и защищает от XSS-атак.

## 2. Типы Токенов

### Access Token

-   **Назначение**: Предоставление доступа к защищенным эндпоинтам.
-   **Срок жизни**: 15 минут.
-   **Передача**: Должен включаться в заголовок `Authorization: Bearer <token>` при каждом запросе к защищенному ресурсу.
-   **Содержимое**: `id`, `login`, `exp` (срок истечения), `type: "access"`, и, что самое важное, `permissions: ["users:view", "users:create", ...]`.

### Refresh Token

-   **Назначение**: Получение нового `access_token` без повторного ввода пароля.
-   **Срок жизни**: 30 дней.
-   **Хранение**: Хранится в `httpOnly` cookie на клиенте и в таблице `user_sessions` в базе данных.
-   **Процесс обновления**: Когда `access_token` истекает, клиент отправляет запрос на `GET /api/v1/auth/refresh`. Сервис проверяет `refresh_token` из cookie в базе данных, и если он валиден, выпускает новый `access_token`.

## 3. Доступ к Защищенным Ресурсам

### Аутентификация (`get_current_user`)

Для доступа к большинству эндпоинтов требуется зависимость `Depends(get_current_user)`.

1.  Зависимость извлекает `access_token` из заголовка `Authorization`.
2.  `JwtProvider` декодирует токен и проверяет его подпись и срок действия.
3.  Из полезной нагрузки извлекается `id` пользователя.
4.  Пользователь извлекается из базы данных и становится доступен внутри эндпоинта.

### Авторизация (`permission_checker`)

Эндпоинты, требующие определенных прав, защищены зависимостью `Depends(permission_checker(["permission_name"]))`.

1.  `permission_checker` — это фабрика, которая создает зависимость с требуемыми разрешениями (например, `["users:create"]`).
2.  Эта зависимость, как и `get_current_user`, получает `access_token` и декодирует его.
3.  **Без обращения к базе данных**, она извлекает список `permissions` из полезной нагрузки токена.
4.  Она проверяет, содержатся ли все требуемые разрешения в списке разрешений пользователя.
5.  Если хотя бы одно разрешение отсутствует, эндпоинт немедленно возвращает ошибку `403 Forbidden`.

Этот подход чрезвычайно эффективен, так как проверка прав доступа не требует дополнительных запросов к базе данных при каждом вызове API.

## 4. Управление Сессиями

Система сессий полностью основана на `refresh_token`.

-   `POST /logout`: Удаляет `refresh_token` из cookie и соответствующую запись из таблицы `user_sessions`.
-   `GET /sessions`: Позволяет пользователю просмотреть все свои активные сессии (например, "вход с Chrome на Windows").
-   `DELETE /sessions/{session_id}`: Позволяет пользователю удаленно завершить любую из своих сессий.
