# Архитектура Фоновых Задач (Celery)

Проект использует `Celery` для выполнения асинхронных и периодических задач. Система разделена на три компонента:
1.  **Backend**: Инициирует задачи и предоставляет API для воркеров.
2.  **Celery Worker**: Выполняет бизнес-логику задач.
3.  **Celery Beat**: Планирует периодические задачи, используя базу данных.

## Компоненты

### 1. Backend (Producer)
Файл: `backend/app/core/celery_client.py`
Отвечает за отправку задач в брокер (Redis). Бэкенд *не импортирует* код задач воркера, чтобы избежать дублирования зависимостей.

### 2. Регистрация Задач (Backend)
Чтобы задача появилась в API (`GET /api/v1/tasks`) и могла быть запущена пользователем, её нужно определить в коде бэкенда.

**Механизм Авто-обнаружения**:
При старте `main.py` вызывает `autodiscover_tasks`. Функция сканирует модули на наличие переменной `TASK_DEFINITIONS`.

Пример (`app/users/ldap/tasks.py`):
```python
class SyncParams(BaseModel):
    dry_run: bool = False

TASK_DEFINITIONS = [
    # (task_name, input_schema, required_permission)
    ("users:sync_ldap", SyncParams, "users:sync")
]
```
Это связывает имя задачи (для Celery), схему входных данных (Pydantic) для валидации API и требуемое разрешение.

### 3. Celery Worker (Consumer)
Директория: `celery_worker/`
Отдельный микросервис, который содержит всю бизнес-логику тяжелых задач (например, синхронизация LDAP, отправка email и т.д.).

**Структура:**
*   `handlers/`: Обработчики задач (бизнес-логика).
    > Полный список доступных задач см. в [Каталоге Обработчиков](worker_handlers.md).
*   `task_registry.py`: Механизм регистрации и автообнаружения обработчиков.
*   `tasks.py`: Точка входа для Celery (`dispatch_task`), которая маршрутизирует задачи на нужный обработчик.

**Процесс выполнения задачи:**
1.  Воркер получает задачу `tasks.dispatch`.
2.  Если задача плановая (`schedule_id`), он запрашивает у Бэкенда параметры и `execution_id`.
3.  Запрашивает необходимые секреты у Бэкенда (через Internal API).
4.  Находит нужный обработчик в реестре и запускает его.

### 3. Celery Beat (Scheduler)
Директория: `celery_beat/`
Отвечает за периодический запуск задач. Использует `DatabaseScheduler` (библиотека `celery-sqlalchemy-scheduler`) для хранения расписания в PostgreSQL.

**Особенности:**
*   Патч для SQLAlchemy 2.0: В `backend/app/core/scheduler_patch.py` реализован патч для совместимости библиотеки с новой версией SQLAlchemy.

## Модели Данных

### История Выполнений (`TaskExecution`)
Файл: `backend/app/tasks/models.py`
Таблица `task_executions` хранит историю всех запусков:
- `id`: UUID задачи.
- `status`: Текущий статус (`PENDING`, `IN_PROGRESS`, `SUCCESS`, `FAILURE`, `REVOKED`).
- `params` / `result`: JSON-поля с входными параметрами и результатом/ошибкой.
- `heartbeat_at`: Время последнего сигнала "жизни" от воркера (используется для обнаружения зависших задач).
- `triggered_by`: Логин пользователя, запустившего задачу (или `system`/`schedule`).

### Планировщик
Используются стандартные таблицы библиотеки `celery-sqlalchemy-scheduler`: `periodic_task`, `crontab_schedule` и т.д.

### Инициализация Периодических Задач
Файл: `backend/app/tasks/initial_data.py`
При первом запуске автоматически создаются записи в таблице `periodic_task`:

1.  **System: Cleanup Zombie Tasks**: Запускается каждые `TASK_TIMEOUT` секунд (по умолчанию 300). Использует `IntervalSchedule`.
2.  **Users: LDAP Sync**: Расписание берется из `LDAP_SYNC_SCHEDULE` (cron-формат). Использует `CrontabSchedule`. Включается/выключается в зависимости от `LDAP_ENABLED`.

Эти задачи можно управлять через админку Celery или напрямую в БД. При перезапуске бэкенда они синхронизируются с текущими настройками.

## Разработка новых задач

1.  Создайте файл с обработчиком в `celery_worker/handlers/<topic>/<task_name>.py`.
2.  Реализуйте функцию-обработчик.
3.  Зарегистрируйте ее через `register_task_handler("task:name", handler)`.
4.  Воркер автоматически обнаружит новый файл при запуске.

## Тестирование

### Celery Worker
Тесты находятся в `celery_worker/tests/`.
*   **Реестр**: Проверяется автообнаружение и регистрация.
*   **Диспетчер**: Интеграционные тесты проверяют полный цикл с моками запросов к Бэкенду.

Запуск тестов:
```bash
cd celery_worker
uv run pytest
```
В конфигурации `pytest.ini` настроено игнорирование предупреждений от устаревших библиотек (`ldap3`/`pyasn1`).

### Backend
Тесты в `backend/tests/test_tasks_schedule_service.py` и `test_scheduler_patch.py` проверяют интеграцию с базой данных расписания.
