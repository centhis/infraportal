# Тестирование Бэкенда

Этот документ описывает архитектуру и рабочий процесс тестирования для бэкенда. Тесты написаны с использованием фреймворка `pytest` и лучших практик для тестирования приложений FastAPI.

## 1. Обзор

Система тестирования спроектирована так, чтобы обеспечить **изоляцию** и **воспроизводимость**. Каждый тест выполняется в чистом окружении, не затрагивая базу данных для разработки.

-   **Инструменты**:
    -   `pytest`: Основной фреймворк для написания и запуска тестов.
    -   `FastAPI.TestClient`: Позволяет отправлять HTTP-запросы к приложению внутри тестов без реального запуска веб-сервера.
    -   `pytest-dotenv`: Используется для загрузки конфигурации тестового окружения.

### `conftest.py` и Фикстуры
Файл `tests/conftest.py` содержит ключевые фикстуры, обеспечивающие изоляцию и удобство тестов.

#### Управление Базой Данных
- **`db_engine`**: Создает Engine для тестовой БД.
- **`run_migrations`**: (`autouse=True`) Применяет миграции Alembic перед запуском сессии тестов и наполняет БД начальными данными (`initial_data`).
- **`db_session`**: Создает новую сессию для каждого теста. **Важно**: Сессия оборачивается в транзакцию, которая откатывается (`rollback`) в конце теста. Это гарантирует, что тесты не влияют друг на друга.

#### Клиент и Override Зависимостей
- **`test_app_client_factory`**: Фабрика, создающая `TestClient`.
    - **Dependency Override**: Переопределяет зависимость `get_db` в приложении FastAPI (`app.dependency_overrides`), подменяя её на тестовую сессию `db_session`. Это заставляет эндпоинты использовать транзакционную тестовую БД.
- **`authenticated_client`**: Создает клиент и автоматически выполняет вход под администратором, устанавливая заголовок `Authorization`.

#### Фабрики Данных
Для создания тестовых объектов используются фикстуры-фабрики:
- **`user_factory`**: Создает пользователя с заданными группами и ролями (динамически создает группы/роли, если их нет).
- **`token_factory`**: Генерирует JWT токены с произвольными permissions и сроком жизни.

## Линтинг и Качество кода

В проекте используется **Ruff** — современный и быстрый линтер.

Запуск проверки:
```bash
uv run ruff check .
```

Автоматическое исправление:
```bash
uv run ruff check . --fix
```

Мы придерживаемся строгих стандартов:
- Отсутствие неиспользуемых импортов.
- Соблюдение PEP 8.
- Отсутствие "мертвого" кода.

### `pytest.ini`
-   `env_files = .env.test`: Главная директива, которая указывает `pytest` загружать переменные окружения из файла `.env.test` перед запуском тестов.
-   `pythonpath = .`: Добавляет корень проекта в `sys.path`, что позволяет тестам импортировать модули приложения (например, `from app.core.config import settings`).

### `.env.test`
Этот файл содержит конфигурацию специально для тестов. Самый важный параметр в нем:
-   `DATABASE_URL`: Указывает на **отдельную тестовую базу данных** (например, `mydatabase_test`). Это гарантирует, что тесты никогда не изменят и не удалят данные, используемые при разработке.

## 3. Ключевые Фикстуры (`tests/conftest.py`)

Файл `conftest.py` является ядром тестовой системы и определяет основные фикстуры, которые подготавливают окружение для каждого теста.

### `run_migrations`
-   **Scope**: `session` (выполняется один раз за всю тестовую сессию).
-   **Autouse**: `True` (активируется автоматически).
-   **Действие**: Перед запуском первого теста выполняет команду `alembic upgrade head`. Это гарантирует, что схема тестовой базы данных всегда соответствует последним версиям моделей ORM. После миграций также вызывается `init_data(db)` для инициализации базовых данных (например, пользователя-администратора, встроенных ролей и разрешений), необходимых для большинства тестов.

### `db_session`
-   **Scope**: `function` (выполняется для каждой тестовой функции).
-   **Действие**: Реализует **полную изоляцию тестов** на уровне базы данных:
    1.  Открывает транзакцию в тестовой БД перед началом теста.
    2.  Передает сессию в тест.
    3.  После завершения теста **откатывает транзакцию** (`transaction.rollback()`).
-   **Результат**: Все изменения, внесенные в базу данных во время теста, отменяются. Каждый тест начинается с абсолютно чистого состояния БД.

### `client`
-   **Scope**: `function`.
-   **Действие**:
    1.  Создает экземпляр `fastapi.testclient.TestClient`.
    2.  **Переопределяет зависимость `get_db`** в приложении FastAPI. Вместо обычной сессии, приложение теперь будет использовать изолированную, транзакционную сессию от фикстуры `db_session`. Это элегантно направляет все API-запросы во время теста в тестовую БД.

### `authenticated_client`
-   **Scope**: `function`.
-   **Действие**: Упрощает тестирование защищенных эндпоинтов.
    1.  Использует фикстуру `client`.
    2.  Выполняет запрос на `/api/v1/auth/login` с учетными данными администратора по умолчанию.
    3.  Извлекает `access_token` из ответа.
    4.  Устанавливает заголовок `Authorization: Bearer <token>` для всех последующих запросов, сделанных с помощью этого клиента.

### `tmp_user`
-   **Scope**: `function`.
-   **Действие**: Создает временного тестового пользователя и добавляет его в группу "admins", делая его доступным для тестов, где требуется пользователь с правами администратора.

### `user_factory`
-   **Scope**: `function`.
-   **Действие**: Фабрика для создания тестовых пользователей с гибкими настройками. Позволяет создавать пользователей с указанными логином, паролем, именем, а также назначать им произвольные группы и роли.
-   **Применение**: Используется для создания тестовых сценариев с различными типами пользователей и их разрешениями.

### `tmp_group`
-   **Scope**: `function`.
-   **Действие**: Фабрика для быстрого создания временных тестовых групп в базе данных. Возвращает объект `Group`.
-   **Применение**: Удобно для тестов, требующих наличия определенных групп.

### `tmp_role`
-   **Scope**: `function`.
-   **Действие**: Фабрика для быстрого создания временных тестовых ролей. Позволяет опционально назначить разрешения новой роли. Возвращает объект `Role`.
-   **Применение**: Используется для создания ролей с нужными разрешениями для тестовых сценариев.

### `tmp_permission`
-   **Scope**: `function`.
-   **Действие**: Фабрика для создания временных тестовых разрешений. Если разрешение с заданным именем уже существует, возвращает его. Возвращает объект `Permission`.
-   **Применение**: Гарантирует наличие необходимых разрешений для тестов.

### `token_factory`
-   **Scope**: `function`.
-   **Действие**: Фабрика для создания JWT-токенов (access и refresh) с настраиваемыми сроками действия и полезными нагрузками.
-   **Применение**: Идеально подходит для тестирования сценариев с истекшими токенами, некорректными токенами или токенами с определенными разрешениями.

## 4. Структура и Запуск Тестов

### Структура (`tests/test_*.py`)
-   Тесты сгруппированы по функциональным областям (`test_auth.py`, `test_rbac.py`).
-   Тестовые функции используют фикстуры, объявляя их в качестве аргументов (например, `def test_login(client: TestClient):`).
-   Тесты следуют классическому паттерну **Arrange-Act-Assert**:
    1.  **Arrange**: Подготовка данных (часто выполняется фикстурами).
    2.  **Act**: Выполнение API-запроса с помощью клиента.
    3.  **Assert**: Проверка статус-кода ответа и содержимого JSON.

### Запуск Тестов
Для запуска тестов необходимо находиться в директории `backend/` и выполнить команду:

```bash
# Запустить все тесты
pytest

# Запустить тесты в конкретном файле
pytest tests/test_auth.py

# Запустить тест по имени
pytest -k test_login_success
```
