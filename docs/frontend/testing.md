# Документация по Тестированию

Тестирование является неотъемлемой частью разработки фронтенда. Оно гарантирует, что компоненты работают корректно, а бизнес-логика выполняется без ошибок.

## Инструменты для тестирования

1.  **Vitest**: Современный и быстрый фреймворк для тестирования, который отлично интегрируется с Vite. Он предоставляет среду для запуска тестов, а также функции для описания тестовых сценариев (`describe`, `it`) и утверждений (`expect`).
2.  **React Testing Library (RTL)**: Библиотека для тестирования React-компонентов, которая поощряет писать тесты, имитирующие поведение пользователя. Вместо того чтобы проверять внутреннее состояние компонента, RTL фокусируется на том, что пользователь видит и с чем взаимодействует.
3.  **JSDOM**: Среда, которая симулирует DOM браузера внутри Node.js, позволяя запускать тесты без необходимости открывать реальный браузер.
4.  **Mock Service Worker (MSW)**: Библиотека для перехвата и мокирования (имитации) API-запросов. Это позволяет тестировать компоненты, зависящие от API, в изолированной и предсказуемой среде.

## Мокинг API (`src/mocks/`)

Ключевым аспектом надежного тестирования является изоляция от внешних зависимостей, в первую очередь — от бэкенд API. MSW решает эту задачу.

**Как это работает:**
1.  **`handlers.js`**: В этом файле определяются "обработчики" для каждого API-эндпоинта, который используется в приложении. Каждый обработчик перехватывает исходящий запрос на определенный URL и возвращает заранее заготовленный (мокированный) ответ.

    ```javascript
    // src/mocks/handlers.js
    import { http, HttpResponse } from 'msw';

    export const handlers = [
        http.get('/api/v1/users', () => {
            return HttpResponse.json({
                users: [{ id: 1, login: 'mockuser' }],
                total: 1,
            });
        }),
    ];
    ```

2.  **`server.js`**: Этот файл создает экземпляр мок-сервера с указанными обработчиками.

3.  **`setupTests.js`**: Этот файл автоматически выполняется перед запуском тестов и настраивает окружение:
    -   `beforeAll(() => server.listen())`: Запускает мок-сервер перед выполнением всех тестов.
    -   `afterEach(() => server.resetHandlers())`: Сбрасывает обработчики после каждого теста. Это гарантирует, что тесты не влияют друг на друга.
    -   `afterAll(() => server.close())`: Останавливает мок-сервер после завершения всех тестов.

## Пример теста

Рассмотрим пример теста для простого компонента `IpAlert`. Файл: `src/components/forms/IpAlert.test.jsx`.

```jsx
import React from 'react';
import { render, screen } from '@testing-library/react';
import IpAlert from './IpAlert';

// Группа тестов для компонента IpAlert
describe('IpAlert', () => {

    // Конкретный тестовый случай
    it('should render with text and title', () => {
        const text = 'This is an alert message.';
        const title = 'Alert Title';

        // 1. Рендеринг компонента
        render(<IpAlert text={text} title={title} />);

        // 2. Поиск элементов на "экране"
        const textElement = screen.getByText(text);
        const titleElement = screen.getByText(title);

        // 3. Утверждения (проверки)
        expect(textElement).toBeInTheDocument();
        expect(titleElement).toBeInTheDocument();
    });
});
```
**Что здесь происходит:**
1.  `describe` группирует тесты для одного компонента.
2.  `it` (или `test`) определяет отдельный тестовый сценарий.
3.  `render` из RTL отрисовывает компонент в виртуальном DOM.
4.  `screen` из RTL предоставляет методы для поиска элементов на отрендеренной странице (например, `getByText`, `getByRole`).
5.  `expect` из Vitest вместе с матчерами из `@testing-library/jest-dom` (например, `toBeInTheDocument`) проверяет, что компонент отображается корректно.

## Тестирование сложных компонентов

При тестировании сложных компонентов, которые содержат вложенную или асинхронную логику рендеринга (как, например, кастомный `TransferList`), важно писать надежные тесты.

-   **Асинхронные обновления**: Используйте асинхронные запросы (`findBy*`) и `waitFor`, чтобы дождаться появления элементов, которые рендерятся после выполнения `useEffect` или получения данных.
-   **Точные запросы**: Избегайте хрупких запросов. Вместо поиска по широким селекторам (`closest('div')`), стремитесь находить уникальный родительский элемент (например, по `aria-label`), а затем используйте `within` для поиска дочерних элементов внутри него. Это делает тесты более устойчивыми к изменениям в верстке.

## Запуск тестов

Для запуска всех тестов в проекте выполните команду:
```bash
npm test
```
Эта команда, указанная в `package.json`, запустит Vitest в режиме однократного прогона.
